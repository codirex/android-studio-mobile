# ADR-0017: Project templates

Status: Proposed

## Context

A new project was only a folder with metadata (ADR-0012). v1.0.0 wants projects of four types, an application, an Android library, a Java library and a Gradle plugin, each with several templates, and a template manager where the user creates and edits templates (roadmap). The template system must not tie the domain to where templates are stored.

## Decision

- `domain:template` (pure JVM) holds the model. A `Template` has an id, a name, the project type it creates, default variables and a list of `TemplateFile`s (a relative path and a text content). Both may contain placeholders.
- Placeholders are written `${name}`. `$$` writes one dollar sign; any other `$` is plain text, so shell and Gradle text stays readable. An unknown name, or a `${` without its closing brace, is an error (`TemplateException`), never an empty string.
- The variables of a project come from its `ProjectSpec`: `projectName`, `packageName`, `packagePath` (the package as folders), `projectType`, and the same name written safely for a Kotlin string (`projectNameKotlin`) and for an Android string resource (`projectNameAndroid`), because project names may contain `$`, quotes and `&`. A template adds its own defaults, such as tool versions. The project's values win over the template's.
- A rendered path must be relative, must not contain `..`, empty segments or backslashes, and must not start in the internal `.asm` folder. The data layer checks it again.
- `ProjectCreator` (domain) is the use case behind the create button. It renders the first template of the type, creates the project, writes the files through the port `ProjectScaffold`, and deletes the project again if writing fails, so a failed creation leaves nothing behind. A template that fails to render stops before anything is created. A type without a template gives an empty project. Failures reach the screen as `ProjectException`, as before.
- Ports: `TemplateCatalog` (the templates of a type) and `ProjectScaffold` (write rendered files into a project). `data:template` implements the catalog with built-in templates written in code; `data:project` implements the scaffold on top of its project locator, with the same guards as the editor's file access.
- Built-in templates are code, not asset files, so they are plain strings that unit tests render and check on the JVM. Custom templates, stored as folders under the app's private files, will produce the same `Template` objects when the template manager comes, behind a second `TemplateCatalog` implementation.
- The built-in templates give small projects that Gradle can build. Tool versions (Android Gradle plugin, compile SDK, AndroidX, Material) are template defaults and will age; they are updated with the IDE.

## Consequences

- The create screen still only picks the project type, so the first template of a type is used. Choosing between several templates is a UI change on top of this model.
- The generated projects cannot be built on the device until the Gradle and SDK steps of v1.3.0 exist; for now they are text the user can read and edit.
- Binary files (icons, a Gradle wrapper jar) are not part of a template yet. The wrapper is generated by Gradle, and icons use vector drawables.

## Open items

- Template manager: create, edit and delete custom templates; export and import.
- A choice of template in the create screen, and template parameters beyond name and package (for example minimum SDK).
- Whether generated projects carry a Gradle wrapper.
